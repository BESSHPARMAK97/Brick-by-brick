# Архитектура

## Аудит исходного состояния (этап 1)

На момент начала работ репозиторий содержал только `README.md` (один коммит `Initial commit`):
кода, конфигурации, базы данных и функций не было. Удалять и мигрировать было нечего,
поэтому стек выбран с нуля:

| Слой | Решение | Почему |
|---|---|---|
| Язык | TypeScript (strict) | Один язык для движка и интерфейса, типы для данных расчёта |
| Интерфейс | React 19 + Vite | Простая сборка в статический сайт, работает без сервера (в т.ч. на площадке без связи) |
| Тесты | Vitest | Тот же конвейер трансформации, что и у Vite |
| Хранение | `localStorage` через интерфейс `KeyValueStore` | Нет сервера; интерфейс позволяет подключить серверное хранилище без изменения логики |
| Экспорт | exceljs (.xlsx), pdfmake (PDF, шрифт Roboto с кириллицей) | Загружаются по требованию, не утяжеляют стартовую страницу |

## Слои

```
src/
  engine/                 расчётный движок (чистый TS, без DOM; детерминированный)
    dates.ts              даты как номера дней, моменты — границы суток
    hash.ts               стабильная сериализация и хэш исходных данных
    types.ts              модель данных: ProjectInput → ScheduleResult
    defaults.ts           исходные данные по умолчанию (минимальный ввод)
    validate.ts           проверка исходных данных
    calendar/             Calendar Engine: праздники РК (из данных), режимы 5/2, 6/1, 7/0, свой режим
    climate/              Climate Engine: климатические нормы, прогноз, модель прочности бетона
    catalog/              Work Catalog: библиотека работ и технологических шаблонов
    schedule/
      network.ts          Technology Engine: развёртывание шаблонов в сеть операций и связей
      resources.ts        Resource Engine: пулы, окна недоступности, учёт загрузки
      scheduler.ts        Schedule Engine: CPM, параллельная SGS с ресурсами, обратный проход
    calculate.ts          оркестратор: объяснения, риски, допущения, достоверность, вопросы
  data/
    calendars/            kz-rules.json (правила Закона о праздниках) + kz-YYYY.json (по годам)
    climate/astana.json   климатические нормы 1991–2020
  storage/projectStore.ts проекты, сценарии, журнал версий, сравнение
  export/                 excel.ts, pdf.ts
  ui/                     интерфейс (React), 9 экранов
tests/                    автотесты движка, хранилища и экспорта
```

Интерфейс вызывает только `calculateSchedule(input)` и хранилище; вся инженерная логика — в `src/engine`.
Даты не генерируются языковой моделью: это детерминированный алгоритм, одинаковые исходные данные и
версия правил (`RULESET_VERSION`) дают идентичный результат (проверяется тестом и хэшами).

## Поток расчёта

1. `validateInput` — проверка данных.
2. `buildNetwork` — для каждой секции и каждого выбранного вида работ создаются экземпляры операций по
   уровням (фундамент → подземные этажи → надземные этажи → захватки), затем связи:
   технологические, межвидовые (фронт работ) с цепочкой альтернатив, «следующий этаж», оборачиваемость опалубки.
3. `findCycle` — циклические зависимости запрещены (ошибка с путём цикла).
4. Прямой проход **без ресурсов** в топологическом порядке + обратный проход → позднее начало каждой операции
   (приоритет для ресурсного расчёта).
5. Прямой проход **с ресурсами** — параллельная схема генерации расписания: в каждый момент времени готовые
   операции рассматриваются по приоритету и начинаются, если все ресурсы свободны на весь период; иначе ждут.
   Если операция ждала ресурс, фиксируется *ресурсная связь* от операции, освободившей ресурс.
6. Обратный проход по технологическим и ресурсным связям → позднее начало/окончание, общий и свободный резерв.
7. Критический путь — операции с общим резервом ≤ 0; ведущая цепочка — от окончания проекта назад по определяющим связям.
8. Объяснение каждой операции, предупреждения, допущения, уровень достоверности, вопросы для шага «Уточнения».

## Календари и климат

* Праздники РК: `kz-rules.json` (перечень по Закону «О праздниках», правило переноса), `kz-YYYY.json`
  (Курбан айт, постановления о переносе). У каждого файла — юрисдикция, год, дата обновления, источники и статус:
  `confirmed` / `secondary` (сверено по вторичным источникам) / `preliminary`. Год без файла — `rule-only`
  (учтены только постоянные праздники, выдаётся предупреждение).
* Перенос считается **для конкретного режима**: при 6/1 суббота рабочая, праздник в субботу переноса не даёт.
* Технологические перерывы (набор прочности) идут в непрерывном времени и не прерываются выходными.
* Климат разделён на: нормы (долгосрочно), снимок прогноза (оперативно, хранится во входных данных),
  ограничения операций (каталог). Зима сама по себе простоев не создаёт: ограничение применяется только к операциям,
  у которых оно задано (например, «мокрый» фасад t ≥ +5 °C), и снимается тепляками/временным отоплением.

## Ресурсы

| Ресурс | Идентификатор | Ёмкость |
|---|---|---|
| Бригады вида работ (по профилям: арматурщики, опалубщики, бетонщики…) | `crew:<вид>:<профиль>` | `resources.crews[вид]` |
| Башенный кран секции | `crane:<секция>` | `cranesPerSection` |
| Бетононасосы | `pump` | `pumps` |
| Поставка бетона | `concrete` | `concreteSupplyM3PerDay`, потребность = объём укладки за смену × доля смены |
| Опалубка стен/перекрытий секции | `wallFormwork:<секция>`, `slabFormwork:<секция>` | число комплектов + связи оборачиваемости |
| Фронт работ этажа | `front:<секция>:<этаж>` | `maxTradesPerFloor` |

Окна недоступности (`resources.unavailability`) обнуляют ёмкость ресурса на период — так моделируются ремонт крана,
отсутствие опалубки, перерыв в поставке бетона. Сроки поставки материалов — ограничения «не ранее» (`constraints`).

## Хранение и версии

`ProjectStore` хранит проекты → сценарии (базовый + альтернативные). Каждый пересчёт с изменёнными данными
сохраняет версию (исходные данные, хэши, сроки операций). `compareSnapshots` / `compareScenarios` показывают
сдвиг окончания, изменённые операции, изменения критичности и перечень изменённых исходных параметров.
Данные не удаляются автоматически, кроме ограничения журнала 50 последними версиями на проект.

## Ограничения текущей версии

* Климат загружен только для Астаны; объект — многоквартирный ЖК.
* Временная дискретность — сутки; частичная смена занимает весь день для последователя (консервативно).
* Резервы при ресурсных ограничениях рассчитываются по сети «технология + ресурсные связи» (стандартное приближение).
* Подвальные этажи — только монолит; отделка и инженерные системы подвала не детализированы.
* Статистика дней с сильным ветром и буранами отсутствует в открытых подтверждённых источниках — вводится пользователем.
